## 1. 模糊根因：patchify（已解决）

ovf 系列（patch1/aux5/geocolor，2026-11-02~03 训练）训练 loss 正常收敛
（patch1: 1.95 → ~0.27 平台）但推理输出整体模糊。根因是 **Wan (1,2,2) patchify
与 GAE latent 分辨率不匹配**：

- GAE-64 codec 网格 27x48，经 (1,2,2) patchify 后每 token 揉进 2x2 = 4 个
  latent 像素（每 token 覆盖约 28x28 像素，而 Wan 预训练每 token 只覆盖
  16x16）；冻结 trunk 无从解块内纠缠，fresh head 只能凭一个向量合成 2x2 块
  → 输出固有低通 → 糊。
- **修复 = patch1 臂**：fresh `Conv3d(64,1536,(1,1,1))` + fresh `Head(patch=1)`、
  `dit.patch_size=(1,1,1)`，每 token 恰好 1 个 latent 像素，奇网格直接吃、
  不再 pad。token 数 336 → 1296/view。三个 patch1 系 run 推理锐度恢复，
  用户确认糊的问题消失。（upsample2 臂为数学等价对照：nearest-2x 上采样后过
  原 (1,2,2)，输出恒为常数 2x2 块，codec 侧 avg_pool 精确还原。）

结论：**分辨率失配的 patchify 是模糊主因，非 loss 加权、非 sigma 分布**。

## 5. 相机控制为什么弱（诊断结论）

按因果排序（`7884 场景`实验证伪了"数据是主因"的假设后修正）：

1. **目标函数结构决定了条件学不出来（主因）**：source 槽位每步被干净地钉在
   输入序列里（`x[:, :, :s] = z` 反复 re-pin），全注意力下"attend 干净 source
   抄内容 + 用小残差解释差异"是最低代价解，任何数据规模下都成立。相机场
   只需解释残差，而残差恰在近视角最小 → 条件通路梯度长期微小。
2. **无显式几何通路**：`warp_mode: none`（父仓库 RGBD 版有 forward-splat，
   相机控制由几何保证；GAE 线去掉了），`rope_frame_axis=view` 只给视图编号
   不携带几何。相机信息只能靠 64ch（add）/294ch 场（concat）从零学一个隐式
   重投影器，冻结的 Wan trunk 没有这个先验。
3. **条件无放大器**：`camera_drop=0, ref_drop=0, eval_cfg=1.0`——没训过
   无条件分支，`v_cond - v_uncond` 方向从未被校准，推理端 CFG 无从放大
   （CFG 只能放大已有条件响应，不能创造响应）。
4. concat@pixel（concatpixel arm，进行中）解决通路带宽（6ch 瓶颈 →
   294ch 独立输入块），但不解决 1-3。

## 6. 修正实验：concat + condition dropout + pose-CFG（已启动）

**代码修正**（commit `4d91a60`）：`WanRGBDNVSTrainingModule._build_flow_input`
的 `cam_drop` 分支在 `plucker_block` 存在时按 batch 元素把整个通道块置零
——add 模式的条件经 `view_condition` 加性进入、原逻辑已覆盖，concat 模式
此前缺这一块（即 concatpixel 配置头注释里"训练端 drop 尚未接"的债）。
修完后训练端 uncond 分支（cam_drop+ref_drop 组合 = `{source=z, target=x_t,
plucker=0}` → ref_drop 后 source 换噪声）与 `sample_latents` 的 eval-CFG
分支**严格一致**。

**配置**：`train_config/normal_config/gae_ovf_re10k_upsample2_concatpixel_drop.yaml`
——与 concatpixel anchor 逐位一致，唯一变量组：

```yaml
camera_drop_prob: 0.2     # GAE flow_gae128 协议
ref_drop_prob: 0.2
eval_cfg_scale: 1.5       # in-training eval 即用 pose-CFG 采样
```

**启动状态**（2026-11-03 15:16）：`logs/ovf_gae_re10k_upsample2_concatpixel_drop`，
日志确认 `CFG condition dropout ENABLED`、`Conv3d(64+294) plucker block
zero-init`，step 10 loss=1.86 正常。多卡启动死在 HCCL 端口绑定（本机 5 个
job 的 comm 占满默认端口池，`HCCL_IF_BASE_PORT` 未生效），改**单卡 NPU4 +
`gradient_accumulation_steps=4`**（有效 batch 仍为 8，~41 s/step）。

**判据**：

- step 200-600 eval（自动带 cfg=1.5）vs concatpixel anchor（无 drop，同协议）：
  LPIPS/PSNR 不应劣化；
- 出 ckpt 后 `infer_trajectory` 后半段 d1 是否脱离 ~0.37 平台；
- cfg 扫描 1.0/1.5/2.0：drop 版应呈单调响应，anchor 应完全不响应——
  即条件方向被成功校准的直接证据；
- 主判据：`tools/diag_pose_sensitivity.py` 的 swap_tgt 敏感度 vs anchor。
